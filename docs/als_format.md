# The Ableton Live `.als` File Format

A reference for the parts of the format that `live_set` reads, based on a survey of 460 real
sets in `$songs`. Where this document and the code disagree, this document is right and the code
is wrong.

`bin/als_files [DIRECTORY]` re-runs the survey. It reads 25 files by default, because reading all
of them takes about four minutes.

---

## 1. The file is gzipped XML

An `.als` file is a gzip-compressed XML document. Read it with:

```ruby
Zlib::GzipReader.open(path, &:read)
```

The root element is `<Ableton>`, and the document is a single `<LiveSet>` under it.

---

## 2. The real Live version is in `Creator`

The `<Ableton>` element has `MajorVersion` and `MinorVersion` attributes, but those are Ableton's
**internal set-format numbers**, not the Live version a user sees. A set written by Live 12.2.1
reports `MajorVersion="5" MinorVersion="12.0_12203"`.

The real version is the `Creator` attribute:

```xml
<Ableton MajorVersion="5" MinorVersion="12.0_12203" SchemaChangeCount="3"
         Creator="Ableton Live 12.2.1" Revision="c0d59beb...">
```

The corpus spans these versions:

| Live version | Sets |
| --- | --- |
| 8.2.1 – 8.3.4 | 21 |
| 11.3.21 – 11.3.22 | 32 |
| 12.0.1 – 12.4.6 | 407 |

### 2.1 Converting a set to Live 11 uses a fixed schema

`live_set -11` writes a set in the Live 11 format, and the version strings it writes are fixed:

```ruby
@ableton['Creator'] = 'Ableton Live 11.3.21'
@ableton['MajorVersion'] = '5'
@ableton['MinorVersion'] = '11.0_11300'
@ableton['Revision'] = '5ac24cad7c51ea0671d49e6b4885371f15b57c1e'
@ableton['SchemaChangeCount'] = '3'
```

These are not configurable, and that is deliberate. A user can ask for "Live 11 format", but
cannot ask for a particular sub-version, so every set the command writes uses the same schema.
The `MajorVersion` and `MinorVersion` values are the internal set-format numbers described above,
not the Live version — which is why `MajorVersion` is `5` for a Live 11 set.

Note that `MinorVersion` here is `11.0_11300` while `Creator` says `11.3.21`. The two are
different numbering schemes: `Creator` is the version of Live that wrote the set, and
`MinorVersion` identifies the set format that Live 11.3.21 reads.

### 2.2 What the conversion removes, and what it keeps

The conversion removes a fixed list of Live 12 constructs that Live 11 does not have:

| Element | Occurrences in the corpus |
| --- | --- |
| `ContentLanes` | top level |
| `ExpressionLanes` | top level |
| `Oversampling` | on audio and MIDI tracks |
| `InstrumentMeld` | 0 — in no set examined |
| `Roar` | 0 — in no set examined |
| `MxPatchRef` | on tracks and the main track |

**Everything else is copied through unchanged.** The conversion is a selective removal, not a
rewrite: it edits the version strings on the `Ableton` element, removes those six elements, and
writes the rest of the document back out.

Two consequences follow.

- **Group tracks are kept**, because Live 11 has group tracks. See section 9.2.
- **An element the conversion has never heard of is kept too.** A `FakeGroup` element, a
  `TrackWrapperType` element, or anything else that a future version of Live writes is copied to
  the output verbatim, with its attributes intact. The conversion does not need to know what an
  element means in order to preserve it.

This is worth knowing if a set contains something the format reference does not document. Nothing
is silently dropped.

## 3. Every value is in a `Value` attribute

This is the single most important fact about the format, and it is easy to get wrong.

**Every value in every `.als` file is stored in a `Value` attribute**, in every Live version from
8.2 through 12.4:

```xml
<EffectiveName Value="My Track"/>
<RelativePath Value="Samples/Imported/song1.mp3"/>
<Freeze Value="true"/>
```

There is no text-only shape in practice. Reading a value with `element.text` returns `""` and
silently produces an empty result.

> **Do not trust `after_real_pain.xsd`.** That file is generated by this project, and
> `generate_xsd` ignores attributes — so it describes every scalar as `xs:string`, which is wrong.
> It is useful for element *structure* and useless for value *shapes*.

`lib/common/xml.rb` provides the reader:

```ruby
xml_value(element)   # the Value attribute, or nil
xml_bool?(element)   # true or false, never nil
```

`xml_bool?` treats a missing element as `false` — an `<AudioTrack>` with no `<Freeze>` element is
not frozen. A value that is neither `"true"` nor `"false"` is also `false`, but it is logged, so
malformed data does not pass unnoticed.

## 4. Track names

A track's `<Name>` element has four children, all `Value` attributes:

```xml
<Name>
  <EffectiveName Value="3-3-Audio 1-1"/>
  <UserName Value=""/>
  <Annotation Value=""/>
  <MemorizedFirstClipName Value="3-Audio 1-1"/>
</Name>
```

| Element | Meaning |
| --- | --- |
| `EffectiveName` | The name Ableton resolved. Accounts for renames, and for the numbering it adds to duplicate tracks. |
| `UserName` | The raw name the user typed. Often empty. |
| `Annotation` | Free text the user typed. Not a name. |
| `MemorizedFirstClipName` | A **clip** name, not a track name. |

`EffectiveName` is the display name. `UserName` is the fallback, and the only one present in Live 8
sets. `Annotation` and `MemorizedFirstClipName` are not names of the track and are not used.

## 5. Clip slots

The session view of a track is a list of clip slots:

```
DeviceChain / MainSequencer / ClipSlotList / ClipSlot
```

**The slot layout did not change between Live 8 and Live 12.** Every slot in every surveyed set
uses the nested form:

```xml
<ClipSlot Id="0">
  <LomId Value="0"/>
  <ClipSlot>
    <Value>
      ... the clip, or nothing ...
    </Value>
  </ClipSlot>
  <HasStop Value="true"/>
  <NeedRefreeze Value="false"/>
</ClipSlot>
```

| Layout | Occurrences |
| --- | --- |
| Nested — `<ClipSlot><Value/></ClipSlot>` | 1896 |
| Flat — `<Value/>` directly in the slot | 0 |

The nested form is sometimes called the "Live 8" layout in this project's code comments. That
label is wrong.

`<ClipSlotList>` also appears under `FreezeSequencer` and `Mixer`; the `MainSequencer` one is the
session view.

## 6. Audio clips live in two different places

This is the part that is easy to get wrong, because a track's audio can be in either place, and
the two places are not versions of each other.

### 6.1 The session view

```
ClipSlotList / ClipSlot / ClipSlot / Value / AudioClip
```

The `AudioClip` is a child of the slot's `Value` element, and is a complete clip in its own right:

```xml
<ClipSlot Id="0">
  <LomId Value="0"/>
  <ClipSlot>
    <Value>
      <AudioClip Id="0" Time="0">
        <LomId Value="0"/>
        <CurrentStart Value="0"/>
        <CurrentEnd Value="92"/>
        <Loop>...</Loop>
        <Name Value="3-Audio 1-1"/>
        <SampleRef>
          <FileRef>
            <RelativePath Value="Samples/Recorded/3-Audio 0001 [2024-11-25 182402]-1.wav"/>
            <Path Value="E:/media/.../3-Audio 0001 [2024-11-25 182402]-1.wav"/>
            <Type Value="1"/>
            <OriginalFileSize Value="525896"/>
          </FileRef>
          <LastModDate Value="1703033260"/>
        </SampleRef>
      </AudioClip>
    </Value>
  </ClipSlot>
</ClipSlot>
```

How often a session slot holds an `AudioClip`:

| Live version | Session slots holding an `AudioClip` |
| --- | --- |
| 11 | yes |
| 12 | 62 of 4206 |

So in Live 12, the session view is usually empty of audio.

### 6.2 The arrangement and the take lanes

```
DeviceChain / MainSequencer / Sample / ArrangerAutomation / Events / AudioClip
TakeLanes / TakeLanes / TakeLane[N] / ClipAutomation / Events / AudioClip
```

All 4657 `AudioClip` elements in the surveyed files are in one of these two places. None are under
a `ClipSlot`.

The arrangement holds the audio on the **timeline** — what you see in the arrangement view. A take
lane holds the audio recorded onto a take. These are different things from the session view's
slots.

### 6.3 The two are not the same clips, and their ids do not overlap

In one file, the session slots are numbered `0`–`7` and the arrangement's `AudioClip` elements
are numbered `140`+. They are separate id spaces, and they hold separate clips.

A track can have clips in both places, and the same audio file can appear in both. The report shows
all three sources, under separate headings:

```text
  Track '3-3-Audio 1-1' **not frozen** (5 clips, 5 files, totaling 13.3 MB)
  Session view: 3 clips, 3 files
    Samples/Recorded/3-Audio 0001 [2024-11-25 182402]-1.wav        6.0 MB  2024-11-25 23:24:02
    ...
  Arrangement: 3 clips, 3 files
    ...
  Take lanes: 3 clips, 3 files
    ...
```

### 6.4 The same file can be referenced several times

A file may be referenced from the session view, the arrangement, and one or more take lanes at the
same time. One track in `above_clouds.als` has 9 clip references to 5 distinct files:

```
3x  Samples/Recorded/3-Audio 0001 [2024-11-25 182402]-1.wav
2x  Samples/Recorded/3-3-Audio 1-1 0003 [2024-11-25 182953].wav
2x  Samples/Recorded/3-Audio 0001 [2024-11-25 182402].wav
```

**A file occupies space once, however many times it is referenced.** So:

- The **clip listing** shows every reference, under the heading for where it came from. The set
  really does contain those references, and the headings make that clear.
- The **total size** counts each distinct file once.
- The **"has not been collected" warnings** name each distinct missing file once, rather than
  repeating itself for every reference to it.

## 7. File references

Inside a clip's `<SampleRef><FileRef>`:

| Element | Meaning |
| --- | --- |
| `RelativePath` | Path relative to the set's directory. Empty when the file is not in the project folder. |
| `Path` | Absolute path. Empty for some references. |
| `Type` | Numeric file type. |
| `OriginalFileSize` | Size in bytes. Live 8 calls this `FileSize`. |

`RelativePath` is empty in 47084 of the surveyed references. A clip whose `RelativePath` is empty
is not collected into the project folder.

### 7.1 The recorded size can be zero, and the file on disk can disagree

`OriginalFileSize` is the size of the *source* file as Live saw it. It is not always the size of the
file on disk, and it is sometimes zero even when the file exists and is not empty.

In one track of `above_clouds.als`:

| File | `OriginalFileSize` | On disk |
| --- | --- | --- |
| `3-Audio 0001 [2024-11-25 182402]-1.wav` | 5,969,624 | 5,969,624 |
| `3-3-Audio 1-1 0006 [2024-11-25 183403].wav` | **0** | 4,027,856 |
| `3-3-Audio 1-1 0007 [2024-11-25 183429].wav` | **0** | 1,499,216 |

The totals disagree too: 6.50 MB summed from the XML against 13.35 MB on disk, for the same 5
distinct files. Live warps, resamples and otherwise processes audio when it saves a set, so the file
on disk is often larger than the source.

**The rule `live_set` follows:** report the size from the XML, but fall back to the filesystem when
the XML says zero and the file is present locally. The XML is the only source that is always
available — the set may have been written on another machine — but a zero is not a useful answer when
the file is right there.

## 8. Devices

**There are no `<Device>` elements in any real set.** The corpus has zero. Plugins are
`<PluginDevice>` elements — 229 of them, in 23 of 40 sampled files.

The plugin's name is not where `live_set` looks for it:

```xml
<PluginDevice Id="6">
  <LomId Value="0"/>
  <Name Value=""/>
  <UserName Value=""/>
  <PluginDesc>
    <VstPluginInfo Id="0">
      <Path Value="C:/Program Files/VstPlugins/MeldaProduction/Pitch Shift/MAutoPitch.dll"/>
      <PlugName Value="MAutoPitch"/>
```

**There are two shapes of `PluginDesc`, and the name is in a different place in each.** Across the
whole corpus:

| `PluginDesc` child | Count | Name element | Live versions |
| --- | --- | --- | --- |
| `VstPluginInfo` (VST2) | 351 | `PlugName` | 8, 11, 12 |
| `Vst3PluginInfo` (VST3) | 1153 | `Name` | 11, 12 |

A VST2 plugin has `PlugName` — 351 of 351 have it, with values such as `"MAutoPitch"`. A VST3
plugin has **no `PlugName` at all** — 0 of 1153 — and its name is at `Name`, with values such as
`"T-De-Esser"`, `"LALA"`, `"Kontakt"`, `"SSQ"`, `"MCompressor"` and `"OTT"`.

```xml
<PluginDesc>
  <Vst3PluginInfo Id="0">
    <WinPosX Value="47"/>
    <NumAudioInputs Value="1"/>
    <NumAudioOutputs Value="1"/>
    <IsPlaceholderDevice Value="false"/>
    <Preset><Vst3Preset/></Preset>
    <Name Value="T-De-Esser"/>
    <Uid Value="..."/>
    <DeviceType Value="2"/>
```

`DeviceType` is `1` for an instrument (96 of 1153) and `2` for an effect (1057 of 1153).

**There is no `Manufacturer` element at all** — it is absent from every plugin in the corpus.

There is also **no reliable way to tell a third-party plugin from an Ableton-native one** from the
XML alone. A native Ableton device is not a `PluginDevice` at all — it is its own element, such as
`Eq8`, `GlueCompressor`, `Limiter`, `Saturator`, `Compressor2`, `Reverb`, `Tube`, `Cabinet`,
`Spectral`, `AutoFilter`, `StereoGain` and `Tuner`. The `PluginDevice` element therefore means
"a plug-in", and every plug-in in the corpus is third-party — but that is a property of the
corpus, not something the file states. `Path` is present on 317 of 1504 plugins and always points
outside Ableton's own directories; the other 1187 have no `Path` at all.

`IsPlaceholderDevice` is `"false"` on 1430 plugins, and absent on the other 74.

The elements `live_set` currently looks for are all absent from real sets:

| Element | Occurrences in 40 sets |
| --- | --- |
| `<Device>` | 0 |
| `<PresetManifestV1>` | 0 |
| `<CurrentPreset>` | 0 |
| `<VstPlugin>`, `<VstPluginCategory>`, `<VstId>` | 0 |
| `<AudioUnitPlugin>`, `<AudioUnitPreset>`, `<AudioComponent>` | 0 |
| `<ClapPlugin>`, `<PluginId>` | 0 |
| `<VstPreset>` | 10, in one file |

See TODO.md N21 for the plan to rewrite this.

### 8.1 The device chain

The devices on a track are the children of `DeviceChain/DeviceChain/Devices`. The path is
doubled: `DeviceChain` (the track's) contains a `DeviceChain` (the chain) which contains
`Devices`.

| Element | Occurrences in 40 sets (audio and MIDI tracks) |
| --- | --- |
| `Eq8` | 179 |
| `PluginDevice` | 153 |
| `GlueCompressor` | 125 |
| `AudioEffectGroupDevice` | 56 |
| `StereoGain` | 37 |
| `MultibandDynamics` | 24 |
| `Saturator` | 24 |
| `Limiter` | 24 |
| `Compressor2` | 18 |
| `DrumGroupDevice` | 16 |
| `Tuner` | 15 |
| `Tube` | 9 |
| `MxDeviceAudioEffect` | 6 |
| `Cabinet` | 4 |
| `Reverb` | 4 |
| `InstrumentGroupDevice` | 4 |
| `Spectral` | 2 |
| `OriginalSimpler` | 2 |
| `AutoFilter` | 2 |

`AudioEffectGroupDevice` is not a device that processes audio itself — it **holds** a group's device
chain, in its branches. See section 9.3.

### 8.2 A device chain can be nested

A chain is not always one level deep. An `AudioEffectGroupDevice` holds a chain in its branches,
at this path:

```
DeviceChain / DeviceChain / Devices / AudioEffectGroupDevice / Branches / AudioEffectBranch /
  DeviceChain / AudioToAudioDeviceChain / Devices
```

The devices inside it are the ones that actually run. A reader that looks only at the top level
of the chain misses them: in a 40-set sample, **14 of the 87 tracks that have a plug-in** hold
their plug-ins only inside a group branch, and no plug-in appears at the top level of their chain.

The same applies to a `DrumGroupDevice`, which holds a drum rack, and an
`InstrumentGroupDevice`, which holds a rack.

**So the devices to report are every device in any `Devices` element, at any depth.** The
container devices themselves are not reported — they are not devices that process audio — but
their contents are.

| Container | Occurrences in 40 sets |
| --- | --- |
| `AudioEffectGroupDevice` | 68 |
| `DrumGroupDevice` | 16 |
| `InstrumentGroupDevice` | 4 |

All 68 of the `AudioEffectGroupDevice` elements in the sample contain devices in their branches.

## 9. Group tracks

A group track is a **summing container**, not a track that plays clips. Ableton's manuals are
explicit about this in both Live 11 (section 16.3) and Live 12 (section 18.3):

> Group Tracks cannot contain clips, but they are similar to audio tracks in that they have mixer
> controls and can host audio effects.

Group tracks exist in Live 11 as well as Live 12. Live 11 sets in the corpus rarely have them,
and 29 of the 32 Live 11 sets in `$songs` were written by `live_set -11` itself, so the corpus
is a poor guide to how common they are. The repo's own `after_real_pain.xsd` includes
`GroupTrack` and `GroupTrackSlot` elements.

### 9.1 A group track has no clips

Measured over the whole corpus:

| Measurement | Result |
| --- | --- |
| `GroupTrack` elements | 1603 |
| `AudioClip` inside any of them | **0** |
| `MidiClip` inside any of them | **0** |
| `GroupTrackSlot` elements | 14031 |
| …that contain a `ClipSlot/Value` | **0** — every one is a bare `<LomId/>` |
| `GroupTrack` with a `DeviceChain/MainSequencer` | **0** |

A group track *looks* like it has a session view. It has a `Slots` element holding eight
`GroupTrackSlot` children, but every slot is empty and has no `ClipSlot` child at all. Its
`DeviceChain` has no `MainSequencer` — it has a `FreezeSequencer` instead, whose `ClipSlotList`
is likewise empty.

**So a group track contributes nothing to clip reporting.** `live_set` ignores group tracks when
it reports clips, their sizes, and whether their samples have been collected.

### 9.2 A group track is not a track in the data model

The membership is a single attribute on the member track. A track's `TrackGroupId` holds the `Id`
of the group it belongs to, and `-1` means it is at the top level.

| Live version | Sets | Sets with groups | Groups |
| --- | --- | --- | --- |
| 8 | 21 | 0 | 0 |
| 11 | 32 | 0 | 0 |
| 12 | 407 | 281 | 1603 |

Groups nest: a group track has its own `TrackGroupId`, so a group can contain another group. In
the sample set `Urban_Agony.als`, group 47 has `TrackGroupId="27"` — it is inside group 27.

A group track has a full mixer, like a regular track: `Sends`, `Pan`, `Volume`, `CrossFadeState`.
That is what makes it a submixer.

### 9.2.1 How nesting is represented

**`live_set` has found no `FakeGroup` element.** There is a claim that the `.als` format uses a
`<FakeGroup>` element — a phantom routing target that wraps a group inside another group. No
such element has been found in any set that has been examined.

That is a statement about the evidence, not a proof of absence. The corpus is one person's
collection, and it holds 314 nested group tracks, so nesting plainly does occur. The evidence
against `FakeGroup` is:

| Check | Result |
| --- | --- |
| The string "fake", any case, anywhere in 460 sets | **0** occurrences — not an element, attribute, or value |
| The string "fake" in the 61,000-line `evasiva.xml` test file in `pyableton` | **0** occurrences |
| `FakeGroup` in the source of `pyableton`, `als-parser`, `abletron`, `AbletonParsing`, `ableton-parser` | **0** occurrences |
| `FakeGroup` in the repo's `after_real_pain.xsd` | **0** occurrences |
| Web search for `"FakeGroup"` with Ableton / Live / `.als` | Nothing but unrelated projects named "fakegroup" |

And the specific elements that the claim names do not appear either. In a 120-file sample:

| Element | Occurrences |
| --- | --- |
| `TrackWrapperType` | 0 |
| `RoutingTarget` | 0 |
| any element matching `*Wrapper*` | only the real ones: `ParametersListWrapper`, `DevicesListWrapper`, `ClipSlotsListWrapper`, `ArrangementClipsListWrapper`, `TakeLanesListWrapper`, `SendsListWrapper`, `ChainsListWrapper`, `ReturnChainsListWrapper`, and others |
| any attribute *value* containing "FakeGroup" | 0 |

The strongest evidence is structural. A nested group and a top-level group have **exactly the
same child elements** — the same 21 of them, in the same order, with the same `*ListWrapper`
elements. The only difference between them is the value of `TrackGroupId` and the routing target.
If `FakeGroup` existed as a structural wrapper, a nested group would have to contain something a
top-level group does not.

What nesting actually uses is the same two mechanisms as everything else in the format: an `Id`
and an `AudioOut/GroupTrack` routing target.

A group track's `TrackGroupId` names its parent group, and `-1` means it is at the top level. Its
`AudioOutputRouting/Target` is `AudioOut/GroupTrack` when it is inside another group, and
`AudioOut/Main` when it is not.

The `Tracks` element is a **flat list**. A group is not a container element in the XML — it is a
sibling of the tracks it contains, and the membership is expressed by attribute. From
`Urban_Agony.als`, in document order:

```xml
<GroupTrack Id="27" ...>            <!-- TrackGroupId="-1", routes to AudioOut/Main -->
  <GroupTrack Id="47" ...>          <!-- TrackGroupId="27",  routes to AudioOut/GroupTrack -->
    <AudioTrack Id="8" ... />       <!-- TrackGroupId="47",  routes to AudioOut/GroupTrack -->
    <AudioTrack Id="46" ... />
    <AudioTrack Id="45" ... />
  </GroupTrack>
  <AudioTrack Id="15" ... />        <!-- TrackGroupId="27",  routes to AudioOut/GroupTrack -->
  <AudioTrack Id="54" ... />
</GroupTrack>
```

(The indentation is for readability only — in the file these are all siblings under `Tracks`.)

So a member's routing target names its **immediate** parent, and the signal path is the chain of
parents: a track in group 47 is routed into group 47, which is routed into group 27, which is
routed into Main.

Two things follow:

- **The hierarchy is recoverable** by following `TrackGroupId` up from a track. Nothing needs to
  be inferred.
- **A track's own routing target is not enough to know its group.** A member routed to
  `AudioOut/GroupTrack` does not say *which* group. That is what `TrackGroupId` is for.

The corpus has **314** nested group tracks — groups whose `TrackGroupId` is not `-1`. Every one of
them routes to `AudioOut/GroupTrack`.

`LinkedTrackGroupId` is **not** the parent indicator, despite the name. It is `-1` for every
group in the corpus — all 1289 top-level groups and all 314 nested ones — so it carries no
information about the hierarchy. `TrackGroupId` is the only thing that does.

There is also a plural `LinkedTrackGroups` element. It appears 439 times in the corpus, and it is
**always empty**.

> **If you have a set that contains a `FakeGroup` element, it is not in the corpus examined
> here, and it would be worth looking at.** Send one to `live_set` and it can be added to the
> survey. Until then, the mechanism described above is what the evidence supports.

A `FakeGroup` element would not be lost by the `-11` conversion, whatever it turns out to be.
The conversion removes a fixed list of six Live 12 elements and copies everything else through
unchanged, so a `FakeGroup` — or any other element the format reference does not document —
survives into the output with its attributes intact. See section 2.2.

A note on naming: `Live_set` has its own `FakeGroup` class in `spec/spec_helper.rb`. It is a
test double — a stand-in for a `LiveGroup` — and has nothing to do with the `.als` format.

### 9.3 A group's devices are in its members' signal path

This is the part that matters, and it is the reason a group track cannot simply be ignored.

A member track's output is routed to its group:

```xml
<AudioOutputRouting>
  <Target Value="AudioOut/GroupTrack"/>
  <UpperDisplayString Value="Group"/>
</AudioOutputRouting>
```

In a 40-set sample:

| Track output target | Tracks |
| --- | --- |
| `AudioOut/GroupTrack` | 543 |
| `AudioOut/Main` | 136 |
| `AudioOut/Track.8/TrackIn` | 2 |

Almost every member is routed into its group: across the whole corpus, **6761 of 6775** group
members route to `AudioOut/GroupTrack`. The 14 that do not are routed to an external output
(`AudioOut/External/S0` and the like), so their audio does not pass through the group.

A group's own output then goes to `AudioOut/Main` (110 groups) or to a parent group (8 groups), so
audio flows up the tree.

A member track holds an `AudioEffectGroupDevice`, and that device holds the group's chain in its
branches. The member's own top-level chain does **not** repeat the group's devices — group 43 in
`Urban_Agony.als` owns `FilterEQ3`, `Limiter`, `PluginDevice` and `Reverb`, and its member tracks
have chains of their own that contain only the `AudioEffectGroupDevice` and, sometimes, a
native device.

| | Group 43 | Member track 30 |
| --- | --- | --- |
| `FilterEQ3` | 1 | 0 |
| `Limiter` | 1 | 0 |
| `Reverb` | 1 | 0 |
| `PluginDevice` | 1 | 0 |

The devices inside the branch are the ones that run. A member's branch holds the group's chain
together with the member's own devices, so the devices to report are at every depth — see
section 8.2.

**Consequence for the Push 3 Standalone check:** a third-party plugin in a group's chain blocks
transfer just as much as one on a track, because the member's audio passes through it. A report
that only inspects member tracks would say "no blocking devices" when the group blocks transfer.
`live_set` therefore checks a group's devices and reports a blocking group device as an error
naming the group and the tracks whose audio it affects.

Across the corpus, 151 group tracks have a `PluginDevice` in their chain.

### 9.3.1 Freezing a member does not get the group's device out of the way

A group track cannot be frozen, so the device cannot be rendered away by freezing the group.
Nor does freezing a member help: a frozen member stays routed into its group, so the group's
device is still in the signal path. All 21 frozen members in the corpus are still routed to
`AudioOut/GroupTrack`.

The remedy is to remove the device from the group's chain, or to bounce the group.

> Note that while Group Tracks cannot be frozen, they can be bounced to audio, which can help
> reduce their CPU load.

— Live 12 manual, section 38.1.4. Bouncing a group is a different operation from bouncing an
individual track: the manual notes that "Group Tracks are bounced post-mixer", so the bounced
audio includes the group's mixer settings and its effects, whereas an individual track is bounced
pre-mixer.


### 9.4 A group track cannot be frozen

> Note that you can only freeze tracks that hold clips, so it is not possible to freeze a Group
> Track, a return track, or the Main track.

— Live 12 manual, section 38.1.4 "Track Freeze". The Live 11 manual (section 33.1.4) says the
same.

A group track holds no clips, so it cannot be frozen. The corpus agrees: **0 of 1603** group
tracks have `Freeze="true"`, and 195 of 195 in a 60-set sample have `Freeze="false"`.

This answers the question of whether freezing a group track also freezes the tracks inside it:
**the question does not arise**, because a group track cannot be frozen at all.

#### 9.4.1 The `Options.txt` hidden option

Ableton's `Options.txt` file can enable "a few experimental and unsupported features". One that
is documented in the wild is `GroupTrackFreeze`, written as:

```text
-_GroupTrackFreeze
```

With it, Live can *bounce* a group as though it were a track. The Live 12 manual's own advice for
groups is to "bounce [them] to audio" rather than freeze them, and the `GroupTrackFreeze` option
is described in the same terms — it enables a group to be treated as a track for bouncing. What
that option does to the XML is a separate matter, and the corpus cannot answer it, because no set
in the corpus has a group track with a populated `FreezeSequencer`.

**`live_set` does not support experimental features.** It ignores `Options.txt` entirely, and
treats every setting that `Options.txt` can control as having its standard behaviour, as though
the experimental option had not been specified. A set that uses `GroupTrackFreeze` is therefore
read as though the group were not frozen, and the group's members are read as unfrozen.

## 11. Frozen tracks and the `FreezeSequencer`

A track that is frozen has a second sequencer. `MainSequencer` holds the editable material;
`FreezeSequencer` holds the rendered audio cache that replaces it during playback. The cache
files live in the project folder under `Samples/Processed/Freeze`.

> When you right-click a track and choose Freeze Track, Ableton does not destroy or replace your
> original data. Instead, it compiles that track into a background audio file and modifies the
> XML layout.

Both sequencers exist at the same time, and a frozen track's clips can be found in either.

Measured over the corpus's 256 frozen tracks:

| | Tracks |
| --- | --- |
| Clips in `MainSequencer` **and** `FreezeSequencer` | 155 |
| Clips **only** in `FreezeSequencer` | **20** |
| Clips only in `MainSequencer` | 0 |
| No clips at all | 81 |

**A frozen track's audio is not always in `MainSequencer`.** `live_set` must look in both places,
or it reports zero clips — and therefore no uncollected-sample warnings and a size of zero — for a
track that is holding hundreds of megabytes of frozen audio.

The two sequencers hold the same kinds of clip. Under `MainSequencer` the paths are:

```
DeviceChain / MainSequencer / ClipSlotList / ClipSlot / ClipSlot / Value / AudioClip
DeviceChain / MainSequencer / Sample / ArrangerAutomation / Events / AudioClip
```

and under `FreezeSequencer` they are:

```
DeviceChain / FreezeSequencer / ClipSlotList / ClipSlot / ClipSlot / Value / AudioClip
DeviceChain / FreezeSequencer / Sample / ArrangerAutomation / Events / AudioClip
```

A frozen track's arrangement clips live under `FreezeSequencer/Sample/ArrangerAutomation/Events`
rather than under `MainSequencer`.

## 12. How `live_set` reads all this

| Element | Read with |
| --- | --- |
| `Name/EffectiveName`, `Name/UserName` | `xml_value` |
| `Freeze`, `IsTempoEnabled` | `xml_bool?` |
| `FileRef/RelativePath`, `FileRef/Path`, `FileRef/OriginalFileSize` | `xml_value` |
| `ClipSlotList/ClipSlot/ClipSlot/Value/AudioClip` | `xpath`, then `xml_value` for the values |
| `ArrangerAutomation/Events/AudioClip`, `TakeLane/ClipAutomation/Events/AudioClip` | `xpath`, then `xml_value` for the values |
| `PluginDesc/VstPluginInfo/PlugName`, `PluginDesc/Vst3PluginInfo/Name` | `xml_value` |
| The devices in a chain | `xml_chain_devices`, which looks in every `Devices` element at any depth |
| `TrackGroupId` | `xml_value`, to find a track's group |
| `AudioOutputRouting/Target` | `xml_value`, to see whether a member is routed into its group |

Do not use `Nokogiri::Slop` accessors for these. A Slop accessor returns a single `Element` for
one match, a `NodeSet` for two or more, and raises `NoMethodError` for none — so the same expression
behaves three different ways depending on the document. `xpath` always returns a `NodeSet`.
