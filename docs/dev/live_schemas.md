# Live Schemas

Every version of Ableton Live ships a description of the ALS XML format, in a
directory of its own:

```text
<Ableton home>/Live 12 Suite/Resources/Schema/
```

These are Live's own description of the ALS XML format. They are not the ALS XML
schemas generated by the [`als_to_xsd` command](../../exe/als_to_xsd). See [XML
Schemas](#xml-schemas), below.

What is known so far is written down here. What is not yet known is tracked as
**TODO L1** in [../TODO.md](../TODO.md).

## Ableton `Schema/` Directory

The directory contains one file per ALS XML format version, named after the
version:

```text
11.0_11300.txt
12.0_12402.txt
9.5_327.txt
```

The name is the format version, and the format version is the `MinorVersion`
attribute of a set. Examples:

- The Live 11 demo set says `MinorVersion="11.0_11300"`, and
`11.0_11300.txt` is the name of the corresponding schema file in the directory.
- The Live 12 demo set says `MinorVersion="12.0_12402"`, and `12.0_12402.txt`
exists too. The schema of a set is therefore a lookup.

Each Live schema file is XML, headed by the format version and two counters:

```xml
<AbletonSchema Version="5" TranslatorNumber="12402" ChangeCount="5">
```

Below that, the elements of the schema are nested with the same hierachry as
found in corresponding ALS XML files. Each elment has elements named `Class` and
`Type`. For example:

```xml
<AdsrScale>
  <EnvTime              Class="TimeableFloat" Type="0" />
  <EnvTimeKeyScale      Class="TimeableFloat" Type="0" />
  <EnvTimeIncludeAttack Class="TimeableBool"  Type="0" />
</AdsrScale>
```

The element `Class` names are the class names of the Live object model that
stores this type of element. For example: `Bool`, `ClassId`, `RemoteableInt`,
and `TimeableFloat`.

## XML Schemas

Currently, this repository generates XML schemas, stored in files with `.xsd`
filetypes, by scanning ALS XML.  XML schemas are different types of artifacts
from Live schemas, and they are not interchangeable.

|                 | The XSDs in `schemas/`          | Live Schemas                                           |
| --------------- | ------------------------------- | ------------------------------------------------------ |
| Origin          | Inferred from the Live sets     | Ableton                                                |
| What they are   | XML Schema, for validation      | A description of the object model                      |
| How complete    | Depends on the origin Live sets | 100% complete for that version                         |
| Where they live | `schemas/`, checked in          | Live installation directory, under `Resources/Schema/` |

The inferred XSDs in `schemas/` is the weaker source because it omits element
types that the scanned Live sets do not contain.

The difference in completeness is not subtle, and it is measurable.
`schemas/vocab_11.3d1.txt` holds the 1875 element names of the inferred Live
11 schema. `schemas/vocab_live11.txt` holds 1989 — 114 more. Every one of
those 114 names (`BandFreq1`, `BasePitch`, `Amplitude`, `Crc`, …) is present in
Live's own schema for 11.0, and none of them is missing from it.

So those 114 names are not stale or mistaken. They are real Live 11 elements
that no Live 11 demo set happens to contain, and the inferred schema cannot
know about them. `BandFreq1` is in none of the Live 11 demo sets, nor in
`sets/live_11/projects_and_als/Fascination.als`.


## What this is good for

The `version_diff` documents enumerate the differences between two versions, and
those differences are currently found by diffing two inferred schemas. Live's
own schemas are the authoritative statement of what each version contains, so
diffing two of them gives the element-level differences directly, without the
inference in the way.

The same applies to the versions with no `version_diff` document yet: Live 8,
Live 9 and Live 10 all have schemas in the directories of the installations
here, so the differences between those versions can be established from the
same source rather than inferred from sample sets.
